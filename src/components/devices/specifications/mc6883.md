# Motorola MC6883: the CoCo's address and video control

The Synchronous Address Multiplexer, or SAM, lets the 6809 and video generator
share dynamic RAM. It supplies multiplexed DRAM addresses, refresh, clock
division, memory selection, and the address sequence consumed by the VDG.
Motorola's [MC6883/SN74LS783 datasheet][manual] describes these coupled jobs.
The [CoCo chapter](../../../machines/6809/coco.md) selects a deliberately
smaller functional model: register writes, address selection, and display
addressing. The board connects either 32 or 64 KiB of logical RAM. DRAM
row/column multiplexing, refresh, bus contention, and individual E/Q clock
transitions are not simulated.

## Sixteen bits, thirty-two write addresses

The SAM has no readable data registers. Writes to FFC0–FFDF select a bit by
address alone: an even address clears it, the following odd address sets it.
The written data byte is irrelevant. Physical reset clears **all** bits;
firmware, rather than construction, selects the familiar 0400 screen page.

| Control bits | Addresses | Meaning |
| --- | --- | --- |
| 2:0, V | FFC0–FFC5 | Display address sequence |
| 9:3, F | FFC6–FFD3 | Display start, in 512-byte units |
| 10, P1 | FFD4–FFD5 | CPU RAM page in a 64 KiB configuration |
| 12:11, R | FFD6–FFD9 | CPU clock selection |
| 14:13, M | FFDA–FFDD | DRAM organization |
| 15, TY | FFDE–FFDF | Normal ROM map or all-RAM map |

```device
device "mc6883"

state {
  register CONTROL: 16
}

action reset "Reset all sixteen SAM control bits" {
  CONTROL <- u16($0000)
}

source validState "Every sixteen-bit control word is representable" : flag {
  return 1
}

source writeControl "Address A4:A1 selects a bit; A0 supplies its value" (address: 8, byte: 8): flag {
  low = select(bit(address, 1), u16($0002), u16($0001))
  pair = select(bit(address, 2), shiftBits(low, left, 2), low)
  nibble = select(bit(address, 3), shiftBits(pair, left, 4), pair)
  mask = select(bit(address, 4), shiftBits(nibble, left, 8), nibble)
  control = register CONTROL
  CONTROL <- select(bit(address, 0), or(control, mask), and(control, xor(mask, u16($FFFF))))
  return 1
}
```

The four selections above decode A4:A1 into a one-hot mask, without a table
of thirty-two nearly identical handlers. Reads leave state untouched and are
unanswered; the board owns the undriven-bus policy.

## Inspection and the selected memory profile

M=00 selects 4K-by-1 DRAM organization, M=01 16K-by-1, M=10 64K-by-1,
and M=11 static-memory operation. Two banks of 16K-by-1 chips provide this
machine's 32 KiB. P1 has no effect with 32 KiB or less on the LS783/MC6883;
Color BASIC nevertheless sets it during initialization. The LS785 variant's
different uses of that bit are not part of this model.

R=00 divides the crystal by 16. R=01 selects that slow E period for CPU
addresses `$0000–$7FFF` and `$FF00–$FF1F`, and crystal/8 elsewhere. In
particular, PIA0 is slow; PIA1, the disk cartridge and vectors are fast.
This is an address decoder, not a test of whether a memory-map route reaches
RAM or ROM. Motorola notes that the MPU presents `$FFFF` during internal
operations, so those cycles are fast too. R=10 and R=11 select crystal/8 for
all addresses. See the datasheet's **MPU Rate Control** and Figure 8.

`cycleTicks` expresses each period in fixed crystal/8 board ticks: two for
slow, one for fast. Its mode argument retains the instruction boundary's
selection even if an instruction writes R. The board combines real CPU
transfers with internal cycles at `$FFFF`; the CPU currently supplies no
dummy-read sequence. Clock-switch stretching and E/Q phase alignment are not
modeled. The resulting elapsed time is an instruction-level approximation,
not a cycle-exact SAM bus simulation.

Fully fast operation steals the VDG/refresh slots on hardware. This model
accounts for its CPU rate, but does not corrupt DRAM or simulate video snow when
software uses it during active display. The frame renderer reads stored RAM;
it does not reconstruct the electrical video bus. Brief fast bursts during
blanking, as used by Fahrfall, can run within that limitation.

The 32 KiB board refuses TY=1 or M=1x. The
[64 KiB board](../../../machines/6809/coco64.md) also supports M=10 dynamic RAM
and both maps; M=11 static-memory operation remains unsupported. TY selects
the all-RAM map independently of M. P1 only changes the CPU RAM page when
M1=1 and TY=0, as shown in the datasheet's Figures 14–17. The logical RAM
approximation omits physical DRAM aliasing for M=00 and M=01.

```device
source videoMode "Inspect V2:V0" : 8 {
  control = register CONTROL
  return truncate(and(control, u16($0007)), 8)
}

source displayStart "F6:F0 selects a 512-byte boundary" : 16 {
  control = register CONTROL
  return shiftBits(and(control, u16($03F8)), left, 6)
}

source page "Inspect P1" : flag {
  control = register CONTROL
  return bit(control, 10)
}

source clockMode "Inspect R1:R0" : 8 {
  control = register CONTROL
  return truncate(and(shiftBits(control, right, 11), u16($0003)), 8)
}

source slowAddress "Address-dependent mode reserves slow cycles for lower memory and PIA0" (address: 16): flag {
  return or(not(bit(address, 15)), equal(and(address, u16($FFE0)), u16($FF00)))
}

source cycleTicks "E period in crystal/8 board ticks, using the boundary's R selection" (mode: 8, address: 16): 8 {
  slow = source slowAddress(address)
  return select(or(equal(mode, u8(0)), and(equal(mode, u8(1)), slow)), u8(2), u8(1))
}

source memoryMode "Inspect M1:M0" : 8 {
  control = register CONTROL
  return truncate(and(shiftBits(control, right, 13), u16($0003)), 8)
}

source normalMap "TY clear selects the ROM-based address map" : flag {
  control = register CONTROL
  return not(bit(control, 15))
}

source supportedMemory "32 KiB profile: normal ROM map with startup or 16K DRAM organization" : flag {
  control = register CONTROL
  return not(or(bit(control, 15), bit(control, 14)))
}

source supported64Memory "64 KiB profile: startup, 16K or 64K dynamic organization" : flag {
  control = register CONTROL
  return not(equal(and(control, u16($6000)), u16($6000)))
}

source upperPage "P1 selects upper physical RAM only with M1 set and TY clear" : flag {
  control = register CONTROL
  return equal(and(control, u16($C400)), u16($4400))
}

source allRam "TY selects RAM reads and writes below the I/O page" : flag {
  control = register CONTROL
  return bit(control, 15)
}

source cpuRamAddress "Translate a RAM-selected CPU address through the page latch" (address: 16): 16 {
  upper = source upperPage()
  return select(upper, or(address, u16($8000)), address)
}
```

## Display rows in physical RAM

The SAM supplies addresses; the VDG interprets the fetched bytes. V selects
how many bytes form a row and how many raster lines reuse it. Figure 5 of the
Motorola datasheet gives the counter dividers and horizontal-sync reset bits.
For the standard matched display modes these produce the following rows:

| V2:0 | Bytes per row | Raster lines per row | Matching VDG modes |
| --- | --- | --- | --- |
| 000 | 32 | 12 | Internal text / SG4 |
| 001 | 16 | 3 | CG1, RG1 |
| 010 | 32 | 3 | CG2, internal text / SG8 |
| 011 | 16 | 2 | RG2 |
| 100 | 32 | 2 | CG3, internal text / SG12 |
| 101 | 16 | 1 | RG3 |
| 110 | 32 | 1 | CG6, RG6, internal text / SG24 |

V=111 is a DMA address sequence, not a supported display mode. The geometry
views return zero for it; the machine rejects it before calculating a frame.
With the VDG still in internal text mode, V=010/100/110 supplies a new
32-byte row every three, two, or one raster lines. These are **extended
semigraphics**: SG8, SG12, and SG24. The VDG keeps its twelve-line character
scan; only the source bytes change more frequently. Its
[chapter](mc6847.md#extended-semigraphics) explains the resulting blocks and
character slices. Odd V values in text mode and mismatched bitmap settings
are not approximated here.

A frame renderer evaluates the current start address and reads RAM directly.
It does not run those reads through the CPU map: even a high F value cannot
access PIAs, acknowledge interrupts, or read ROM. The device produces a sixteen-bit physical display address independent of P1
and TY. The board masks it to the installed RAM capacity: the 32 KiB profile
discards bit 15, while the 64 KiB profile retains it.
`displayAddress` takes a **memory row**, not a raster line, and a byte column.
Visible coordinates depend on the selected mode; it does not clip them.

Hardware loads the display counter at a field boundary and advances it with
VDG timing. This untimed view takes an instantaneous frame instead; changes
halfway through a scan and refresh addresses are not modeled.

```device
source displayBytesPerRow "V selects sixteen or thirty-two bytes; DMA has no display row" : 8 {
  mode = source videoMode()
  return select(equal(mode, u8(7)), u8(0), select(bit(mode, 0), u8(16), u8(32)))
}

source displayLinesPerRow "Standard matched modes repeat each byte row for twelve, three, two, or one raster lines" : 8 {
  mode = source videoMode()
  highResolution = select(equal(mode, u8(7)), u8(0), u8(1))
  bitmap = select(lessThan(mode, u8(3), unsigned), u8(3), select(lessThan(mode, u8(5), unsigned), u8(2), highResolution))
  return select(equal(mode, u8(0)), u8(12), bitmap)
}

source displayAddress "Address a byte within the physical 64 KiB display address space" (row: 8, column: 8): 16 {
  start = source displayStart()
  stride = source displayBytesPerRow()
  offset = add(multiply(row, stride), extend(column, 16))
  return add(start, offset)
}

interface Mc6883 {
  size 32
  initialize reset
  reset reset
  validate validState
  write * writeControl
  view videoMode
  view displayStart
  view page
  view clockMode
  view slowAddress
  view cycleTicks
  view memoryMode
  view normalMap
  view supportedMemory
  view supported64Memory
  view upperPage
  view allRam
  view cpuRamAddress
  view displayBytesPerRow
  view displayLinesPerRow
  view displayAddress
}
```
