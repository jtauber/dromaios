# Motorola MC6847: characters, semigraphics, and bitmap pixels

The MC6847 Video Display Generator turns RAM bytes into a television picture.
Its internal character generator contains 64 uppercase letters, digits, and
symbols. A byte can instead describe four coloured blocks, allowing text and
simple graphics to share one screen. The [Motorola datasheet][manual], Figures
19–21 and the alpha/semigraphics mode tables, is the hardware reference.

This decoder implements internal alphanumerics, inverse video, both text
colour sets, semigraphics-4, and all eight bitmap graphics modes. It supplies
colour indices for a 256-by-192 active raster, and declares the NTSC sync periods
used by the CoCo board clock. An optional NTSC artifact-colour approximation
interprets pairs of RG6 dots. Borders, full composite waveform encoding and
decoding, external character ROMs, and semigraphics-6 are not modeled. This is
the original MC6847 character set, not the later MC6847T1's additional text modes.

## Connections, not CPU registers

The CoCo connects PIA 1 PB7 to A/G, PB6:4 to GM2:0, and PB3 to CSS. In alpha
mode GM2:1 is immaterial, but PB4 also drives INT/EXT: it must be low for
internal characters and SG4. Video RAM bit 7 drives A/S, and bit 6 drives INV.
The [Tandy technical reference][technical], pages 21–24, describes this wiring.
These views take the resolved PIA pins and the fetched byte explicitly. There
are no retained values in this combinational decoder, and observing it cannot
change the PIA, SAM, RAM, or CPU.

```device
device "mc6847"

state {
}

action reset "The combinational decoder has no retained state" {
}

source validState "There is no retained decoder state" : flag {
  return 1
}

source alphaMode "A/G low selects text and semigraphics" (pins: 8): flag {
  return not(bit(pins, 7))
}

source internalText "PB4 also drives INT/EXT; low selects internal characters and SG4" (pins: 8): flag {
  return and(not(bit(pins, 7)), not(bit(pins, 4)))
}

source semigraphics "A/S comes from screen byte bit 7" (byte: 8): flag {
  return bit(byte, 7)
}

source glyph "The low six bits address the internal character generator" (byte: 8): 8 {
  return and(byte, u8($3F))
}

source characterCode "Map the internal glyph order to printable ASCII" (byte: 8): 8 {
  glyph = and(byte, u8($3F))
  return select(lessThan(glyph, u8($20), unsigned), add(glyph, u8($40)), glyph)
}
```

## Text and inverse video

The 5-by-7 glyph starts two pixels from the left and three lines down within
the cell. The bitmap row supplied to `textPixels` already includes those
blank margins; bit 7 is the leftmost pixel. INV inverts the **whole** cell,
including the margins. Thus bytes 00–3F show bright characters on dark
backgrounds, and 40–7F show dark characters on bright backgrounds. Ordinary
Color BASIC text uses the latter. CSS selects green (0) or orange (1), each
with distinct bright and dark shades.

The [character bitmap data](../mc6847-character-set.ts) retains the first 64
glyphs from MAME 0.250's original MC6847 table, with its BSD-3-Clause notice.
Its later lower-case extension is excluded. `characterCode` is an inspection aid, not a
host-font renderer: glyphs 1E and 1F depict up and left arrows.

```device
source textPixels "INV reverses glyph and margin pixels" (byte: 8, glyphRow: 8): 8 {
  return xor(glyphRow, select(bit(byte, 6), u8($FF), u8($00)))
}
```

## Four blocks per byte

With A/S high, bits 3:0 enable the top-left, top-right, bottom-left, and
bottom-right blocks respectively. Each block is four pixels wide and six
lines high. Bits 6:4 select one of eight colours; a disabled block is black.
INV and CSS do not alter this interpretation.

```device
source semigraphicsPixels "Two four-pixel blocks on each half of the cell" (byte: 8, row: 8): 8 {
  upper: flag = lessThan(row, u8($06), unsigned)
  left: flag = or(and(upper, bit(byte, 3)), and(not(upper), bit(byte, 1)))
  right: flag = or(and(upper, bit(byte, 2)), and(not(upper), bit(byte, 0)))
  return or(select(left, u8($F0), u8($00)), select(right, u8($0F), u8($00)))
}

source foreground "Eight SG4 colours, or bright green/orange text" (byte: 8, pins: 8): 8 {
  colour = and(shiftBits(byte, right, 4), u8($07))
  return select(bit(byte, 7), colour, select(bit(pins, 3), u8($07), u8($00)))
}

source background "SG4 uses black; text uses dark green or dark orange" (byte: 8, pins: 8): 8 {
  return select(bit(byte, 7), u8($08), select(bit(pins, 3), u8($0A), u8($09)))
}
```

## Bitmap graphics

With A/G high, every bit in a fetched byte is pixel data. GM2:0 chooses the
resolution and packing below. The mode names follow Motorola's tables: CG
means four-colour graphics, RG resolution graphics. All modes occupy the same
active picture; lower resolutions repeat each logical pixel horizontally and
vertically. The SAM must supply the corresponding byte rows, as specified in
its [chapter](mc6883.md); the VDG does not select their memory addresses.

| GM2:0 | Mode | Pixels | Bits per pixel | Bytes per row | Frame bytes |
| --- | --- | --- | --- | --- | --- |
| 000 | CG1 | 64 × 64 | 2 | 16 | 1,024 |
| 001 | RG1 | 128 × 64 | 1 | 16 | 1,024 |
| 010 | CG2 | 128 × 64 | 2 | 32 | 2,048 |
| 011 | RG2 | 128 × 96 | 1 | 16 | 1,536 |
| 100 | CG3 | 128 × 96 | 2 | 32 | 3,072 |
| 101 | RG3 | 128 × 192 | 1 | 16 | 3,072 |
| 110 | CG6 | 128 × 192 | 2 | 32 | 6,144 |
| 111 | RG6 | 256 × 192 | 1 | 32 | 6,144 |

GM0 selects the packing: zero takes pairs 7:6, 5:4, 3:2, 1:0; one takes
individual bits 7 down to 0. Both start at the left. CSS low selects green,
yellow, blue, red for the four pair values; CSS high selects buff, cyan,
magenta, orange. In resolution modes zero is black and one is green or buff.
These are direct VDG colours. A television can interpret the RG6 bit pattern
as additional colours, as described below.

```device
source graphicsMode "GM2:0 selects the bitmap format" (pins: 8): 8 {
  return and(shiftBits(pins, right, 4), u8(7))
}

source graphicsWidth "CG1 has 64 pixels; RG6 has 256; the other modes have 128" (pins: 8): 16 {
  mode = source graphicsMode(pins)
  return select(equal(mode, u8(0)), u16(64), select(equal(mode, u8(7)), u16(256), u16(128)))
}

source graphicsHeight "GM groups select 64, 96, or 192 pixel rows" (pins: 8): 8 {
  mode = source graphicsMode(pins)
  return select(lessThan(mode, u8(3), unsigned), u8(64), select(lessThan(mode, u8(5), unsigned), u8(96), u8(192)))
}

source graphicsBitsPerPixel "GM0 selects one-bit resolution or two-bit colour pixels" (pins: 8): 8 {
  return select(bit(pins, 4), u8(1), u8(2))
}

source graphicsColour "Shift the requested pixel to the left edge, then apply CSS" (byte: 8, pixel: 3, pins: 8): 8 {
  dots = iterate(extend(pixel, 8), byte) {
    return select(bit(pins, 4), shiftBits(dots, left, 1), shiftBits(dots, left, 2))
  }
  palette = select(bit(pins, 3), u8(4), u8(0))
  return select(bit(pins, 4), select(bit(dots, 7), palette, u8(8)), add(palette, shiftBits(dots, right, 6)))
}
```

`graphicsColour` takes pixel indices 0–7 for resolution modes or 0–3 for
four-colour modes. Indices 4–7 in a four-colour mode shift out all data and
return that palette's colour zero. The geometry and pixel views describe GM
regardless of A/G; the machine only uses them when A/G is high.

## NTSC artifact colours

RG6 puts 256 dots on a line: two dots per VDG clock, with the same nominal
3.58 MHz clock frequency as NTSC's colour subcarrier. Alternating dark and
light dots therefore produce a repeating signal at the colour frequency. A
colour television can interpret that brightness pattern as chroma. These are
**artifact colours**, not extra colour bits stored in video RAM.

The black/buff colour set (A/G=1, GM=111, CSS=1) is the useful case here.
The VDG and colour reference can start in either of two relative phases,
swapping blue and orange/red. This is why some games ask the player which
colour is visible at startup. The [XRoar manual][composite-reference] explains
both phases and distinguishes its coarse two-bit renderer from fuller signal
models. The phase in this model is an explicit **display choice**, stable
until changed, not a random reset side effect or a new device register.

### The chosen pair approximation

We interpret each even/odd pair from the left edge of a scan line and fill
both output positions with one symbolic colour. This gives 128 colour cells
across a 256-dot raster. No emulator or ROM state changes when the display
interpretation changes.

| Left/right dots | Normal phase | Reversed phase |
| --- | --- | --- |
| 00 | Black | Black |
| 01 | Artifact blue | Artifact orange/red |
| 10 | Artifact orange/red | Artifact blue |
| 11 | White/buff | White/buff |

“Normal” names our chosen presentation convention; neither phase is universally
correct for every CoCo or program. Pairs are bits 7:6, 5:4, 3:2, and 1:0 of
each fetched byte. Byte boundaries and scan-line starts are pair boundaries,
so pairing never carries into the next byte or row. Repeated `$55` and `$AA`
produce the two colours; `$00` and `$FF` remain black and white/buff.

This is a functional **two-dot approximation**, not an analogue NTSC decoder.
It omits filtering, fringe colours, cross-pair interactions, and sub-pixel
phase. For example, `01 10` produces two coloured cells even though its middle
two dots are adjacent; `00 11` produces black then white. Real televisions do
not divide the waveform into independent pairs. CSS=0, text, semigraphics,
and the lower-resolution modes retain their direct colours in this profile;
we do not claim that their real composite signals have no artifacts. PAL
and monitor-specific colour response remain outside the model.

```device
source artifactMode "A/G=1, GM=111, CSS=1 select the modeled NTSC artifact mode" (pins: 8): flag {
  return equal(and(pins, u8($F8)), u8($F8))
}

source artifactPairColour "Approximate an even/odd dot pair, most significant pair first" (byte: 8, pair: 3, reverse: flag): 8 {
  dots = iterate(extend(pair, 8), byte) {
    return shiftBits(dots, left, 2)
  }
  evenOn: flag = bit(dots, 7)
  oddOn: flag = bit(dots, 6)
  colour = select(xor(oddOn, reverse), u8($0B), u8($0C))
  return select(not(xor(evenOn, oddOn)), select(evenOn, u8(4), u8(8)), colour)
}
```

The mode view owns eligibility; the pair view only interprets the supplied
bits. Pairs 0–3 are visible; indices 4–7 shift out every dot and return black.
Both are read-only. The machine selects direct or composite rendering,
reads physical RAM through the same SAM addresses, and supplies pairs to this
view only in the declared mode. The browser supplies approximate RGB values
for the symbolic blue and orange/red, just as it does for the direct colours.

## NTSC sync periods

The original MC6847 repeats a field every 262 lines. FS is low for 32 lines;
HS is low for 16.5 VDG clocks. Motorola's Figures 7–8 give these widths. Its
printed 227.5-clock line period disagrees with measured CoCo operation: the
[MAME device implementation][mame-timing] records the correction to **228**,
including software that relies on 57 normal-speed CPU clocks per line. This
model uses 228, not the MC6847Y's different field length.

The following half-clock units preserve the fractional HS width. These are
periods, not retained counters: the machine owns elapsed time and derives
phase from it. The CoCo wiring places FS transitions on HS falling edges.
Electrical propagation delays, analogue waveform shape, and pixel fetch timing
are outside this digital, instruction-boundary model.

```device
source lineHalfClocks "228 VDG clocks per line" : 16 {
  return u16(456)
}

source horizontalSyncHalfClocks "HS is low for 16.5 VDG clocks" : 8 {
  return u8(33)
}

source fieldLines "The original NTSC MC6847 has 262 lines per field" : 16 {
  return u16(262)
}

source fieldSyncLines "FS is low for 32 lines" : 8 {
  return u8(32)
}
```

| Index | Colour |
| --- | --- |
| 0–7 | Green, yellow, blue, red, buff, cyan, magenta, orange |
| 8 | Black |
| 9 | Dark green |
| A | Dark orange |
| B | Artifact blue |

changing emulation state; no measured NTSC colours are claimed. The native
renderer rejects unsupported SAM/VDG combinations before reading screen data.
